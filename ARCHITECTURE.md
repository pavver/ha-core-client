# ha-core-client Architecture

This library is designed with type safety, asynchronicity, and resilience to network failures as core principles.

## Core Components

The crate has two layers. **`Session`** (`src/session.rs`) is a synchronous, sans-IO state machine holding all protocol logic. **`HAClient`** (`src/client.rs`, `src/runner.rs`, `src/connection.rs`, feature `runtime`) is a Tokio transport around it. The sections below describe the behaviour, which lives in `Session`; "the runner" there means the `Session` driven by the `Runner` task. Section 7 describes the split.

### 1. Handle/Runner Pattern (Actor Model)
*   **`HAClient` (Handle, `src/lib.rs`)**: holds an `mpsc::Sender<Command>` and an `Arc<Shared>` (config, shutdown signal, connection-state `watch`). Cloning is cheap. Every method sends a `Command` (`src/subscription.rs`) carrying a `oneshot` responder and awaits it with the request timeout.
*   **`Runner` (Actor, `src/runner.rs`)**: a single background task that owns the WebSocket and all state (subscriptions, in-flight requests, per-connection message ids). No locks are needed. Request results stay raw JSON (`RawValue`) in the runner and are decoded by the calling task, so a huge `get_states` answer does not stall events or pings.
*   The runner keeps only a *weak* sender, so it shuts down when every user handle is dropped. Callbacks get a temporary strong handle while they run.

### 2. Connection Lifecycle
*   `HAClient::connect` performs the first connect and authentication itself (`src/connection.rs`), so a wrong URL or token is returned to the caller instead of being retried.
*   `HAClient::connect_lazy` skips that: the runner is spawned with `ws = None` and starts in the offline phase with an immediate first attempt (`ConnectionState::Connecting`, no backoff delay). A failed attempt continues as `Reconnecting { attempt: 1 }` with backoff; `auth_invalid` is terminal as in any reconnect. Commands are handled by the same offline handling.
*   `wait_for_connection` is implemented in the handle (`call_waiting` in `lib.rs`), not in the runner: it waits on the state `watch` until `Connected` (within the budget), then sends. If the runner still answers `NotConnected` (the connection dropped again) and budget remains, it waits again. Nothing is sent while waiting, so `NotConnected` keeps its meaning; the request timeout starts at the hand-over.
*   A **session** runs while connected: `select!` over shutdown, incoming frames, commands and a housekeeping tick.
*   A session ends on a `Close` frame, read/write error, or a missing `pong`. All in-flight requests then fail with `ConnectionLost`, and the runner enters the **offline** phase: exponential backoff with jitter, then reconnect. The backoff starts over only after a session that lasted at least `min(reconnect_max_delay, 60s)`, so a server that drops the connection right after `auth_ok` is not hammered. While offline, commands are answered immediately with `NotConnected`.
*   `auth_invalid` during a reconnect is terminal (`ConnectionState::AuthFailed`), because retrying a revoked token only risks an IP ban.

### 3. Message Ids and Subscriptions
*   Triggers are sent with the `trigger` key, so Home Assistant 2024.10+ is required; `connect` logs a warning for an older `ha_version`.
*   Home Assistant requires message ids to strictly increase per connection, so ids restart at 1 on each connection.
*   Each subscription has a stable client-side id (the `Subscription` handle) plus the Home Assistant message id on the current connection. A `routes` map translates the latter back to the former.
*   On reconnect, all subscriptions are re-sent in creation order (a `BTreeMap`). A re-subscription that Home Assistant rejects is logged and dropped.
*   `subscribe_*` calls complete when Home Assistant acknowledges them, so configuration errors reach the caller. Handing the `Subscription` back goes through `Runner::confirm`: if the caller stopped waiting, the subscription is removed (queue discarded) and unsubscribed, since nobody could ever unsubscribe it.
*   Subscriptions learn about the connection through `SubEvent::Status`, which goes through the same per-subscription queue as data events: `Interrupted` when a session is lost, `Restored` once re-acknowledged, `Rejected` if Home Assistant refuses the re-subscription (it is then dropped), `Unsubscribed` after `unsubscribe`, `Closed` when the client stops.
*   A `Subscribe` received while offline, or still unanswered when the connection drops, is registered locally (marked interrupted, `Interrupted` delivered) and sent by the next `resubscribe`.
*   For `subscribe_entity`, the caller's responder is carried by the initial `Resync` read, so a missing entity fails the call (both server-side subscriptions are then unsubscribed).
*   Entity subscriptions keep their last seen state. After `subscribe_entity` itself, the runner reads the entity with a one-shot `subscribe_entities` (`PendingKind::Resync`) as the baseline. After a reconnect, all entity subscriptions share **one** read: `resubscribe` records them in `Runner::restoring`; an acknowledged one moves to `restore_acked` and its live trigger events are held (`SubEntry::held`); a rejected, unsubscribed or otherwise removed one leaves the set (`forget_restore`), and so does one whose re-subscription timed out (it is retried; a late ack then gets a batch read of its own), so one unanswered re-subscription cannot keep the others waiting with their events held. Once `restoring` is empty (`send_restore_read`, checked after each result, command and housekeeping tick), one `subscribe_entities` lists every distinct entity id (`PendingKind::ResyncBatch`). Its event is applied per subscription (`apply_resync`): a difference from the last seen state is delivered as one `StateChange`, then `Restored`, then the held events the read does not already cover (`covered` compares `last_updated`); then the read is unsubscribed. If the read fails or times out, each subscription just gets `Restored`. Only `resubscribe` fills `restoring`, so there is one batch per connection, plus one per retried re-subscription that is acknowledged after it. Outside a restore, an event for the exact update already in `last_state` is skipped (the read and the trigger can both report it). A re-subscription that times out is sent again on the same connection (neither dropped nor forcing a reconnect, which would interrupt every other subscription); the id of every expired request that creates a server-side subscription is kept in `Runner::expired_subscribes` (cleared per connection), so if Home Assistant accepts the old request late, the duplicate is unsubscribed on that `result`, not only on its first event (which a rare trigger might never send).
*   **Why live entity events come from a `state` trigger, not `subscribe_entities` (deliberate choice).** `subscribe_entities` looks attractive: its initial snapshot would make the resync free and remove the trigger + read pair. It does filter by `entity_ids` server-side, so only the requested entities reach the client. The cost is on the Home Assistant side: `handle_subscribe_entities` registers `hass.bus.async_listen(EVENT_STATE_CHANGED, …)` and checks `entity_ids` inside the callback, so every such subscription runs for every state change of every entity. One subscription per `subscribe_entity` would make N subscriptions do N checks per state change, on installations with thousands of entities. A `state` trigger goes through `async_track_state_change_event`, which dispatches by `entity_id`, so its callback runs only for its own entity. That is why `subscribe_entities` is used only for one-shot reads (`get_state`, `Resync`, the batched `ResyncBatch` after a reconnect), which are unsubscribed right after the first event. It suits one long-lived subscription covering many entities at once (a state mirror), not one subscription per entity. Checked against `homeassistant/components/websocket_api/commands.py` (`dev`, 2026-10).
*   Home Assistant may send a subscription's first event before its `result` (`render_template` does). Events for an id still in `PendingKind::Subscribe` go to `SubEntry::early` and are queued after the ack (after `Restored` on a reconnect); for entity subscriptions they become held events (restore) or are covered by the baseline read.

### 4. Request Bookkeeping
*   Every sent request has a `Pending` entry with a deadline. The housekeeping tick expires overdue entries (`Timeout`) and drives the `ping`/`pong` keep-alive.
*   Each write is bounded by `pong_timeout`; a blocked write (half-open connection) ends the session.
*   Server-side subscriptions the client no longer routes (one-shot reads, unsubscribed, timed out) are unsubscribed once (`PendingKind::Unsubscribe`); their ids sit in `orphans` so late events are ignored, and are removed when Home Assistant confirms (nothing arrives after that answer).
*   The session `select!` is not `biased`, so a steady stream of frames cannot starve commands or the housekeeping tick.
*   A `Drop` guard on the runner sets `ConnectionState::Stopped` if the task ever ends without `finish` (a panic), so waiters are released.
*   `get_state` uses a one-shot `subscribe_entities`: the ack is followed by an event with the compressed state, after which the client unsubscribes.

### 5. Type-Safe Protocol
*   **`protocol.rs`**: builders for outgoing messages and one `Incoming` struct for everything Home Assistant sends.
*   **`state/`**: enums for domains, services, entity states and attribute values. String-valued enums are generated by `string_enum!` with an `Other(String)` fallback, so unknown values round-trip instead of failing.
*   **`events/`**: the public event types (`StateChange`, `ServiceCall`, `BusEvent`, `TriggerFired`, `TemplateUpdate<T>`, `Silence`, `Update<T>`) and the crate-private `SubEvent` the runner and queue work with. `SubKind::convert` turns each payload into a `SubEvent`: bus events (`Bus`, or `StateChanged`/`ServiceCall` for the typed kinds), entity state triggers (`StateChanged`), other triggers (`TriggerFired`), `render_template` results (`TemplateRendered`/`TemplateError`, or `Silence` for `watch_silence`). Attributes are typed by the entity's domain (`AttributeSet::for_entity`, also for history entries) and parsing never fails; values that do not fit the typed schema are kept untyped.

### 6. Sources, Callbacks and Streams
*   **`Source<T>` (`src/source.rs`)** is `{ kind: SubKind, request, convert: fn(SubEvent) -> Option<T> }`. The runner only sees `kind` and `request`; `convert` maps the runner's `SubEvent` to the user's type. `None` means a data event that does not fit (malformed payload, a non-bool silence result): it is logged and skipped. `Status` events never go through `convert`; they become `Update::Status`.
*   `Command::Subscribe` carries a `Delivery`. `Delivery::Callback` wraps the user's typed callback with `convert` (`HAClient::subscribe`), so **the conversion runs in the subscription's worker task**, never in the runner. `Delivery::Stream` spawns no worker: the `QueueRx` stays in `SubEntry::stream_rx` and `Runner::confirm` hands it to the caller inside `Subscribed { subscription, rx }`. Offline and in-flight subscribes go through the same `confirm`, so streams work in every path.
*   **`EventStream<T>` (`src/stream.rs`)** wraps the `QueueRx` in `stream::unfold` and applies `convert` in `poll_next`. It ends when the runner drops the `QueueTx` (after the last status) and the queue is drained. Dropping it calls `unsubscribe_detached`. It holds an `HAClient`, so it keeps the client alive; `Shared::workers` does not count it, so `stop()` does not wait for it.
*   **`WeakClient`** holds a `WeakSender<Command>` plus `Arc<Shared>`; `upgrade` gives an `HAClient` while any user handle exists.
*   Each subscription has a worker task that runs its callbacks one at a time, in event order. Each callback runs in its own spawned task, so a panic is contained and logged. A callback running longer than `slow_callback_warning` is logged once when it crosses the threshold and again when it finishes.
*   Runner and worker are connected by a bounded queue (`src/queue.rs`). The runner never waits on it. When a callback falls behind, entity subscriptions merge the newest `StateChanged` into the queued one; other subscriptions drop their oldest data event past `subscription_queue_size`. Status events bypass the limit. `queue::Filter` has two independent flags: `merge` and `state_only`. `merge` is on for entity subscriptions unless `Source::without_merging` cleared it (`SubKind::EntityState::merge`); without it the queue drops the oldest data events like any other. `state_only` is set for `EntityChanges::State` subscriptions: the queue drops changes that keep the state string and, when merging, also a merge that cancels out (`A → B → A`), which also covers the post-reconnect `StateChanged`; the server-side trigger gets `to: null` so attribute-only changes are not even sent. The count of merged/dropped events is handed to the callback as `SubscriptionStatus::Lagged` before the next event.
*   The worker holds only a weak command sender, so queued events don't keep a dropped client alive.
*   `Shared::workers` counts live workers; `stop()` waits for it to reach zero (bounded by 5s). Callbacks run inside the `IN_CALLBACK` task-local, so `stop()` called from a callback skips that wait instead of waiting for itself.
*   Callbacks return `CallbackResult` (`Result<(), BoxError>`), so the public API does not depend on `anyhow`.
*   Callbacks receive an `HAClient` handle, so they can call Home Assistant themselves without deadlocking the runner.

### 7. Sans-IO `Session` and the Tokio Transport

*   **`Session` owns everything that was the runner's state** (subscriptions, `pending`, `routes`, `orphans`, `expired_subscribes`, `restoring`/`restore_acked`, per-connection ids) **and the connection lifecycle**: the `auth_required` → `auth` → `auth_ok`/`auth_invalid` handshake, the `ha_version` check, the backoff and the stable-session rule, and the terminal `AuthFailed`/`Stopped` states. It never does I/O, never reads the clock (every entry point takes `now: std::time::Instant`, kept in `Session::now` so internal handlers need not pass it around) and never blocks. Handlers that were `async` because of a send are plain functions: `send_raw` appends the frame to an outbox.
*   **Host interface.** `poll_action(now)` yields `Action::Connect` (when the first connect or a backoff delay is due; the phase becomes `Connecting`) and `Action::Close` (the session ended the connection itself: pong timeout, protocol error, bad token, `stop`). `on_connected` starts the handshake, `on_frame` feeds text frames, `on_activity` counts other frames as a sign of life, `on_disconnected` reports a failed connect, a `Close` frame or a socket error (ignored if the session already ended that connection, so a host that reports a failure it was told about is harmless), `tick` runs housekeeping (timeouts, ping/pong, connect timeout), `poll_transmit` drains the outbox, `next_wakeup` says when the next tick matters. The outbox is cleared whenever a connection ends, so frames of a dead connection never reach the next one. Bounding a write is the host's job; a failed or stuck write is `on_disconnected`.
*   **Phases:** `Disconnected { connect_at }` → `Connecting` → `Handshake` → `Connected`, and `Terminal`. Commands in any phase but `Connected` get the offline rules (`NotConnected`, subscriptions registered `Interrupted`); in `Terminal` they fail with `Stopped`. `ConnectionState` is derived by the session (`Connecting`, `Reconnecting { attempt }` stays through backoff and the next attempt, `Connected` is set once the re-subscription frames are queued).
*   **Results without async.** The session still answers through `tokio::sync::oneshot` responders (they need no runtime; that is why the crate keeps `tokio` with the `sync` feature only). `HAClient` awaits the receivers; the sans-IO API wraps them in `Reply<T>` (`try_recv`, with a conversion such as `parse_states`), and `PendingSubscription<T>` / `SessionEvents<T>` do the same for subscriptions. A request whose `Reply` was dropped before submission is not sent (existing `is_closed` rule); a subscription whose `PendingSubscription` is dropped before the ack is removed and cancelled (`confirm`). `SessionEvents` reads the same per-subscription `queue` as a worker would (`QueueRx::try_recv`), so merging, `Lagged` and the status events behave identically.
*   **`Delivery`** is `Stream` (the `QueueRx` goes to the caller) or `Worker(FnOnce(QueueRx))`; `HAClient::subscribe` passes a closure that spawns the callback `Worker`, so the session itself never spawns tasks.
*   **The Tokio `Runner`** is the transport: while no connection exists it asks `poll_action` and, for `Connect`, opens the WebSocket (bounded by `connect_timeout`) while answering commands through the session; with a socket it `select!`s over shutdown, frames, commands and an interval tick, calling `on_frame`/`handle_command`/`tick` with `tokio::time::Instant::now().into_std()` (so paused test time moves the session), and flushes the outbox before waiting again, each write bounded by `pong_timeout`. The handshake runs through the same loop, so it is just the session in `Handshake`. `HAClient::connect` runs the handshake on its own (`connection::connect_and_auth`) so that errors reach the caller, then hands the authenticated session to the runner. The runner publishes `Session::connection_state()` to the `watch` after each step.
*   **Feature `runtime`** gates `HAClient`, `Runner`, `connection`, `stream`, the domain helpers, `SubscriptionGuard`, `TlsConnector` and the `tokio-tungstenite`/`futures-util` dependencies. Without it, `cargo build --no-default-features --target wasm32-wasip2` builds `Session`, `Source`, `state`, `events`, `triggers`, `protocol`, `Target` and `Error`. Doctests that use `HAClient` need the feature.
*   **Not in the sans-IO API (yet):** `get_history` / `get_state_at_time`, `call_service_with_response`, domain helpers and `EventStream`. They are thin layers over `command`, which can be used meanwhile.
